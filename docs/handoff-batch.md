## 第一部分：车次窗排布、PIS 空框、机场晚间间隔、存车线长度、帮助窗口透出提示

### 1. 车次窗排布（`src/ui/trackview.ts`，`placeTrainWindow` 和 `leaderG`）

现象：
- 广兰路—唐镇一带，有个车次窗被挤到远处，一条长斜线连回车头，和别的窗口、线路交叉，很难看。截图里是 009-1021，挂在唐镇下行车头上，窗口却放在广兰路下方。
- 「012-存车」「048-存车」「029-存车」这几个，文字超出了方框。

要求：
- 车次窗先放在本车正上方（上行）或正下方（下行），引线只是一小段竖线。
- 位置冲突时，按离车头的距离一层层往外叠放，不要横着甩到远处。
  - 引线不许穿过其他车次窗，也不许和其他引线交叉；
  - 窗口中心和车头的横向偏移不超过一个窗口宽。
  - 实在放不下，就允许窗口压住线路，不要拉长斜线。
- 方框宽度按实际文字的渲染宽度来量，中文「存车」和数字同样处理，不许按字符数估算。
- 只改排布，车次窗的内容和颜色不变。

验证：
- 加一个纯函数测试：给一组挤在一起的列车位置，断言没有交叉、横向偏移在上限内、方框宽度不小于文字宽度。
- 浏览器里截广兰路到创新中路这一段看一眼（3 小时视图，晚上 23 点左右，有存车的时候），截图放进 `work/`。

### 2. 站台 PIS 空框的写法（`src/ui/pisview.ts`）

用户说现实里的屏是这样的：
- 某一框没有列车信息时，时间显示 `00:00`，「开往」「To」后面空着；
- 不会出现「今日无后续列车」「今日末班车已开出」「暂无列车信息」「首班车 hh:mm」「下一班列车 hh:mm」这类提示。

字段实拍也能对上：`docs/field-2026-10-16-pis.md` 里有 1 号框显示 00:00 的记录。

要改的：
- `emptyText()` 这套提示全部去掉。空框统一显示倒计时 `00:00`，下面是「开往」/「To」，终点空着。
- 「本站列车通过不停车」不放在框里。如果滚动通知栏里还没有这条，就加进通知栏。
- 首末班那一页（`selectPisFirstLast`）不动。
- 第二个框轮换 2nd/3rd 的问题：截图里远东大道上行一班车都没有，第二个框却显示「第三班列车(3rd)」。只有真有第三班车时才轮换到 3rd，否则一直是「第二班列车(2nd)」。
- 相关测试的预期值会变，汇报里逐条说明。

### 3. 浦东机场晚间间隔和高德对不上

现象：
- 用户截了 23:12 浦东1号2号航站楼下行站台的 PIS（那天是 10 月 19 日，工作日），第一班车倒计时还有 19:38。
- 用户另外给了一张高德截图，方向是蟠祥路往浦东机场，23 点那一小时的到站时刻是：23:00、23:03、23:06、23:08、23:10、23:14、23:19、23:22、23:27、23:32。
- 截图没写是哪一站。从这串时刻看，大约比 `reference/timetable-gaode/海天三路-DN-weekday.txt` 晚 2–3 分钟，所以按浦东1号2号航站楼到站处理，标【假设】，只用来交叉核对。

要做的：
1. 先量数据，再下结论。生成工作日计划，列出 22:00–24:00 远东大道、海天三路、浦东1号2号航站楼下行的到站时刻。和高德文件、上面那串时刻逐条对齐，算出间隔差。
2. 计划本身就对不上：找出是哪条规则把晚间往机场的车排少了，比如交路或者收车规则。修规则本身，不许为了对上这几格去加车或改时刻。
3. 计划对得上，但 PIS 显示错了：问题在 PIS 取车，比如终点站进站台怎么选下一班。修 `src/sim/pis.ts`。
4. 两种情况都要跑 `validate-plan`（两种日型）、`firstlast`、`gaode-compare`，按 AGENTS.md 的验证要求来。结论连同前后数字写进汇报。

### 4. 存车线画得比车短、站台方框宽窄不一

现象：用户截图里，存车线上的车次图形超出了画出来的存车线，伸进了道岔区。截图是 G05xx 一带，有中间两股存车线、往上接出入段线，应该是淞虹路，你按区段名确认一下。

原因：D96 以后，车次图形的长度统一按站台长度来画；可示意图上，有些存车线、折返线画得比站台短。

要求：
- 定一条通用规则：凡是能停整列车的泊位（存车、折返、热备），示意图上画出来的长度不得短于车次图形的长度。不够的，在布局里把这段画长。
- 不要单独给淞虹路加特例，也不要把车次图形截短。
- 站台方框也统一宽度。用户问「为什么站台长度会不一样」。原因是示意图不按比例：`trackview.ts:346` 按真实的 188 m 用 `chainX` 换算，每站的像素每米不同，所以各站方框宽窄不一。车次图形取的是其中最短的一个（`geometry.ts:302`）。
  - 改成：所有站台方框都画成同一个像素宽度，中心仍在真实站台中心。用户指出：全线站台都按 8 节 A 型车建，只会比车长，远东大道画得最短纯粹是示意图比例造成的。
  - 统一宽度不要迁就最窄的站。取一个在默认缩放下看着合适的固定像素宽度，写成一个常量；空间不够的站，比如远东大道那种两边站距长、中间还有出入段道岔的，由布局给它让出位置。
  - 车次图形长度 = 统一站台宽度 × 车长 / 站台长度。车停站时，图形和方框的比例在每站都一样。
  - 方框宽度和 `trainLength()` 共用同一个来源，同一件事只算一处。
- 写一个测试，遍历所有整列车泊位，断言画出来的长度不小于 `trainLength()`；再断言所有站台方框宽度相等。
- 改完截一张淞虹路的图放进 `work/`。

### 5. 帮助窗口里透出区段提示

## 第二部分：开局设置与一天里的随机性

用户要的是：每次开一个运营日都不一样。开局时选好想要哪些教员事件、要不要随机故障。事件在一天里随机发生，也可能不发生。客流总量每天在一个范围内浮动。

### 1. 开局对话框（`src/ui/app.ts` 的「运营日设置」）

现有的日期、节假日、开始时刻、自动应答、驾驶模式都保留，另外加两项：

- **随机故障**：一个下拉框，选项是关、轻、中、重，对应 `SimConfig.randomFaults` 的 0–3。这个字段和引擎里的处理已经有了（`engine.ts:238`），这里只是把选项挪到开局对话框。教员页里现有的随机故障按钮保留，开局之后照样能改。
- **教员事件**：按类别分组列出复选框，比如设备故障、列车故障、客流、天气、施工。另有「全选」和「全不选」，默认全不选。

两项的选择都存进 localStorage，下次打开对话框时自动带出上次的选择。

### 2. 教员事件改成在一天里随机发生（`src/sim/scenario.ts`）

现在的事件写在 `SCENARIOS` 里，每个都固定在「场景开始后第几秒」触发。要改成下面这样：

- **事件库**：把各场景里的事件拆出来，做成一张数据表 `INSTRUCTOR_EVENTS`。每条写明 id、名称、类别、`run(sim)`，再加上下面两项：
  - **可发生时段**：写成数据，按事件本身的性质来定。例如：
    - 早高峰大客流只在早高峰时段；
    - 「上行首班车故障」只在首班车前后；
    - 「施工延时销点」只在运营开始前后；
    - 天气类全天都可以。
    - 时段写成数据，不许在代码里按站名或钟点写分支。
  - **发生概率**：先统一用 0.5，标【假设】。表里每条都可以单独改。
- **排期**：开局时，对每个勾选的事件按概率决定今天发不发生。发生的话，在「可发生时段」与「开始时刻到运营结束」的交集里均匀抽一个时刻；交集为空就不发生。
  - 抽签用独立的随机数流，从 seed 派生，参照 D63 他线晚点用 `seed ^ 常数` 的做法，不许扰动主仿真的随机序列。
  - 排好的时刻表要存进配置或检查点，保证回放、导出诊断、重放诊断能复现同一天。
- **对用户保密**：事件发生之前，界面和事件日志里都不出现它的时刻。发生的时候照现在的样子记一条「教员」日志。
- **评分**：现有的场景评分按场景时长结算。随机事件改成在当天结束时汇总，或者教员点「结束评估」时汇总，列出今天发生了哪些事件、各自处置得怎样。尽量沿用现有的报告结构，不另起一套。
- **原来的预设场景**：教员页里的固定场景（比如龙阳路早高峰加车）保留，作为可复现的训练题。这些场景的事件改为从事件库里引用，同一个事件只写一处。

### 3. 客流总量每天浮动

- 现在 `RIDERSHIP_TARGET`（`src/sim/calibration.ts:4`）是固定值，工作日 109 万。改成一个范围：每天开局时在范围内抽一个当天的目标值。
- 用户举的例子是 105 万到 115 万。范围先取中心值 ±5%，标【假设】，写成数据，工作日和双休日按同一条规则。
- 抽签同样用从 seed 派生的独立随机数流。抽出来的值进入 `passengerScale`，这个字段已经存进检查点（`state.ts:38`）。
- 小时内、各站之间的波动保持现在的样子（`passengers.ts:71`）。
- 每天抽到的目标值在开局日志里记一条 I 级「客流」事件。

### 完成标准

- 同一个 seed、同样的勾选，跑两遍得到的事件时刻表和客流目标完全一样；换一个 seed 就不一样。写单元测试证明这一点。
- 勾了事件但概率抽签没中的，一整天都不发生；抽中的在它的时段内发生。写测试。
- 全不选、随机故障关闭时，同一 seed 下运行图的 `trips` 和 `blocks` 哈希和改前完全一致。客流目标会变，这是这次要的结果，汇报里说明。
- `npx tsc --noEmit` 干净；跑 `tests/scenarios.test.ts`、`tests/core.test.ts`，以及你新增的测试文件。
- D 条目由 Claude 写，你在汇报里列出用了哪些【假设】。

### 不要做的

- 不改运行图生成、运行时分、停站模型。
- 不改现有故障的处置逻辑，只改它们什么时候、要不要被触发。
- 不跑 `npm test`、soak、simday。

## 第三部分：运营日切换会丢车

用户在 120× 下跑过午夜。到 10-20 04:06 时，一列从北翟路车辆段往蟠祥路上行的列车「突然消失」，右栏显示「列车已不在线」。这列车是用户自己加开的。

已查明的：
- `src/sim/worker.ts:249`：到 27:45，worker 直接用第二天的日期新开一个运营日（从 04:00 开始，seed+1）。还在动的列车全部丢弃，第二天的过夜位置来自新运行图，不是前一天列车实际停在哪里。
- 工作日和双休日的计划里，没有任何车次在 26:30 以后结束（探针在 `work/probe/late.ts`）。会在 03:45 还在跑的，只有加开、晚点或调整留下来的列车。

要做的：
1. **加开时提示**：加开的车次如果会在 27:45 之后才结束，加开的时候就提示用户：它会在运营日切换时被收掉。仍然允许加开。
2. **切换不能悄悄丢车**：
   - 切换前如果还有列车不在过夜位，记一条 B 级「运营」事件，列出车号、位置、正在执行的任务。
   - 切换本身记一条 I 级事件，比如「运营日切换：10-19 → 10-20」，界面给一个提示。
   - 切换前自动把前一天的诊断数据保存一份，用户事后还能导出。现在一切换前一天的状态就没了，没法查。
3. **切换时带上用户的选择**：现在 `start()` 只带了自动应答和随机故障。驾驶模式（`driveMode`）、第二部分新增的教员事件勾选，都要带到第二天。用的是同一份配置，不要另写一份。

完成标准：加开一列跨过 27:45 的车，加开时有提示，切换前后的事件日志能说清它的去向；切换后前一天的诊断能导出；切换后驾驶模式不变。

## 第四部分（最后做）：打包成桌面 app，一键启动

用户要的是：不开命令行、不输网址，双击桌面图标就能打开模拟器。只给用户自己用，不发布。

### 做法（已定）

用 Tauri 2 包现有的 Vite 前端。本机已有 Rust（cargo 1.97）、VS 生成工具、WebView2（155），不用另装运行时。前端代码不用改，`vite.config.ts` 已经是 `base: './'`。

1. 新建 `src-tauri/`，用官方的 Vite 集成：
   - `beforeDevCommand: npm run dev`、`devUrl: http://localhost:5173`；
   - `beforeBuildCommand: npm run build`、`frontendDist: ../dist`。
   - `@tauri-apps/cli` 加进 devDependencies。Rust 侧只要最小的 `main.rs`，不加业务逻辑。
2. 窗口设置：
   - 标题「上海地铁2号线 ATS 模拟器」，启动时最大化，最小尺寸按现在页面不出横向滚动条来定；
   - 关闭窗口就退出进程，不常驻托盘。
3. 图标：自己画一个简单的 SVG（绿色 2 号线圆标加白色「2」就行），用 `npx tauri icon` 生成各尺寸。不要用上海地铁官方标志。
4. `package.json` 加两个脚本：
   - `app:dev`：`tauri dev`；
   - `app:build`：`tauri build`。只要 release exe，不要安装包，用 `--no-bundle` 或 `bundle.active: false`。
5. 一键启动：新增 `scripts/app-shortcut.ps1`。它在桌面建一个快捷方式，名字「2号线ATS」，指向 `src-tauri/target/release/` 下的 exe，图标用 exe 自带的。
   - 以后更新只要重新跑一遍 `npm run app:build`，快捷方式不用重建。
   - exe 名字用英文，比如 `line2-ats.exe`，避免路径编码问题。
6. `.gitignore` 加上 `/src-tauri/target/` 和 `/src-tauri/gen/`。`Cargo.lock` 要入库。

### 启动流程和启动速度

- **启动流程**：打开 app 就直接弹出「运营日设置」对话框，让用户选几号、几点开始，选完才开始生成运行图。不要先自动开一个默认的运营日。网页版行为不变。
  - 开局对话框里新增的随机故障、教员事件两项在 第二部分 里，不在这个任务的范围内。
- **启动速度**：先量，再优化。分段记下冷启动的耗时，写进汇报，改前改后各一份：
  1. 双击到窗口出现；
  2. 窗口出现到对话框可以操作；
  3. 点「开始」到运行图生成完；
  4. 运行图生成完到预热推演结束、画面开始走。
  - 只优化量出来最慢的那一两段。运行图生成大约 4 s，这一段不许为了变快而改变结果：改前改后的 `trips` 和 `blocks` 哈希必须一致。
  - 加载期间要有进度提示，显示当前在哪一步，不能只有一块黑屏。
- **界面**：这次只做启动对话框和加载画面，让它们像个正式的 app。主界面其他地方不动，用户点名的显示问题在 第一部分 里另做。

### 必须在 app 里验证的几件事

浏览器里能用、WebView2 里不一定能用的东西，逐条在打包出来的 exe 里检查，不要只跑 `app:dev`：

- **Web Worker**：仿真在 worker 里跑（`worker: { format: 'es' }`）。确认 exe 里时钟会走，120× 不卡。
- **声音**：`public/sounds/` 下的切片会跟着 `dist` 打进 exe，这是给用户自己用的，可以。确认车内广播、站台广播和 VVVF 都能播。WebView2 的自动播放策略可能要求先有用户操作，沿用现在的音频解锁逻辑，别绕过它。
- **IndexedDB**：`src/sim/warmupCache.ts` 用 IndexedDB 缓存预热检查点。确认第二次启动时命中缓存。
- **localStorage**：界面设置关掉 app 再打开要还在。
- **导出诊断**：`src/ui/store.ts:154` 用 `<a download>` 导出 `line2-diagnostics-*.json`。
  - WebView2 下如果点了没反应，或者文件不知道存到了哪里，就改成 Tauri 的保存对话框（`plugin-dialog` 加 `plugin-fs`）。
  - 只在 Tauri 环境下走这条路，网页版保持原样。判断用 `'__TAURI_INTERNALS__' in window` 这类官方方式，同一件事只写一处。
- **字体**：`@fontsource/jetbrains-mono` 是本地打包的，确认没有去外网取资源。CSP 保持默认的严格设置，哪条被拦了就只放开哪条。
- **开发者工具**：release 版关掉；`app:dev` 里可以开。

### 完成标准
