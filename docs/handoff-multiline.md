# 任务：多线路——第一阶段，选线骨架

**开工时机**：等 `docs/handoff-runtime-and-diagram.md` 的「第一部分补充二」交付、审完提交以后再开工。这个任务会动几十个文件，不要和补充二混在同一份未提交改动里。

## 方向（用户决定，2026-10-23）

- 同一个软件里选线：启动时选一条线，各线独立运行。几条线在同一个世界里同时跑，是用户以后的规划，现在不做；但这次的结构不能把它堵死。
- 要做的线路，要能覆盖上海现有的几类信号制式和自动化等级，另外要有带分叉的线路。

按 `reference/shanghai-lines-signalling-operations.md`，候选代表线路是：

| 线路 | 形态 | 信号 | 实际运营自动化等级 | 覆盖的类型 |
|---|---|---|---|---|
| 2号线（已有） | 直线 | CBTC，TBTC 后备 | GoA3 DTO | CBTC、DTO；后备是准移动闭塞 |
| 14号线 | 直线 | CBTC | GoA4 UTO | UTO（车上有随车人员，平时不开车，用户 2026-10-23 确认） |
| 10号线 | Y 形，龙溪路分叉 | CBTC | GoA4 UTO | 分叉 + UTO |
| 11号线 | Y 形，嘉定新城分叉 | CBTC | GoA2，司机监护 ATO | 分叉 + GoA2 |
| 5号线 | Y 形，东川路分叉 | 双 CBTC | GoA3 DTO | 分叉 + DTO |
| 3号线 | 直线，宝山路—虹桥路与 4号线共线 | TACS | GoA2 | TACS |

阶段顺序（每个阶段单独出任务文档，做完停下汇报）：

1. **选线骨架**（本文）：线路数据可替换，2号线结果完全不变，再用一条最小测试线证明代码里没有藏着 2号线的假设。
2. **14号线**：直线，不用动拓扑，先把 UTO 做出来，包括唤醒和休眠、自动出入库、OCC 远程处置、随车人员接管后降为人工驾驶。数据来源：`reference/line14/line14-layout-pdf.md`、`reference/line14/`、官方首末班。
3. **分叉拓扑**：线路从一条里程轴改成图。先做 10号线，因为 UTO 已经在第 2 阶段做好，这里只新增分叉；然后做 11号线和 5号线。
4. **TACS**：3号线，与 4号线共线的区段怎么处理，到时候再定。

## 本阶段要做的

### 1. 线路数据集中到一处

- 2号线的全部数据放进 `src/data/lines/line2/`，包括：
  - 现在的 `line2.ts`、`firstlast.ts`、`lasttrains.ts`；
  - 2号线专用的音频库，`soundbank`、`onboardbank`、`doorbank`、`vvvf`、`ridelog`、`onboardfield1021` 里属于 2号线的部分。
- 还有散落在仿真和界面代码里的 2号线数据，也要搬进去。已知的有：
  - `src/sim/timetable.ts` 的 `TERMINAL_DEPOT`：按车站序号写的；
  - `src/sim/calibration.ts` 的 `PEAK_SECTION`；
  - `src/sim/holiday.ts` 的各站客流加强；
  - `src/sim/pis.ts` 的目的地规则；
  - `src/sim/scenario.ts` 里带站码的场景；
  - `src/sim/gradient.ts` 的车站埋深表；
  - `src/sim/connections.ts` 的换乘线路；
  - 界面上的标题、线路标志 `line2-badge.png`、线路色。

  这份清单不全，要自己用 grep 扫一遍：2号线站码、站名、车站序号常量都要找。
- 搬完以后，`src/data/lines/` 以外的代码不许出现 2号线的站码、站名或车站序号常量。注释里拿 2号线举例可以留。写一个测试把这条守住，比如扫源码里的站码列表。
- 某条线没有的功能，比如 TBTC 后备、热备车、跨日的特殊车次，在数据里写成空，不许在代码里写 `if (line === 2)`。

### 2. 当前线路怎么选

技术方案你定，下面几条要满足：

- 在启动时选一次：页面用 `?line=` 参数，传给 worker；Node 脚本和测试用参数或环境变量；不指定时默认 2号线。
- 换线要重新加载页面，不做运行中热切换，免得两条线的状态混在一起。
- 现有的 `import { STATIONS } from ...` 写法，最好只改路径，不改调用方式，这样改动最小。
- 线路编号要进这些地方：预热检查点的键（`warmupCache.ts`）、存档、诊断导出、inputLog。回放时必须知道是哪条线。
- 菜单里加「线路」选项，选了就重新加载。标题、标志、线路色都从数据里取。

### 3. 定义 `LineData` 类型

- 包含 2号线现有的全部数据。
- 另外加两个字段，填 2号线的值：信号制式（CBTC，TBTC 后备）和运营自动化等级（DTO）。行为上还按现在的代码走，这一阶段不改。
- 结构要给分叉留余地：车站和里程以后会按支线分，所以新写的代码判断前后方向，一律走 `topology.ts` 的方向辅助函数（AGENTS.md 硬规矩第 7 条）。这一阶段不实现分叉。

### 4. 最小测试线

- 加一条明显是虚构的测试线，名字就叫「测试线」：五六个站，两端各有折返，一个车辆段，简单的首末班和间隔。
- 不放进正式菜单，只给测试和开发模式用。
- 测试要覆盖：
  - 拓扑能建出来；
  - 两种日型的计划 `validate-plan` 都是 0 error；
  - 跑一整天加第二天，0 完整性违例。
- 测试线跑不通，就说明某处藏着 2号线的假设。找到的修法和 2号线一样：搬成数据，或者改成通用规则。每处在汇报里列一行。

## 不要做

- 不改 2号线的任何行为。运行图、时分、ATS、车载、界面显示都和改前一模一样。
- 不做 14号线的数据，不做 UTO，不做分叉拓扑，不做多条线同一个世界。
- 不动 `reference/line14/`。

## 验证

- 2号线：改前改后分别生成两种日型的计划，`trips` 和 `blocks` 的哈希必须完全一致。`validate-plan`、`firstlast`、`gaode-compare` 三个脚本的输出也要和改前一致。
- `npx tsc --noEmit`；改到的测试文件逐个跑，再加上测试线的新测试。
- `scripts/fuzz-day.ts` 后台跑一小批 2号线种子，要带第二天、天气和调度操作，0 完整性违例。如果有失败，用改前代码跑同一个种子，看是不是原来就有的问题。
- 搬出去的表，前后内容逐项一致。汇报里列出「原来在哪 → 现在在哪」。

## 汇报

按 AGENTS.md 的格式。另外要列出：
