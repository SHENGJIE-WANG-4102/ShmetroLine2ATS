## 4. 前后接续的教员事件被拆散了

- 前后接续的步骤合成一个事件，内部按原来的相对时间依次执行，例如「大风过程」。其他场景照这个原则逐个检查：

  - 能独立成立的，单列，比如大客流、道岔失表。
- 事件 id 改成能看出内容的名字。现在的 `rmg-surge-2` 实际是「列车乘客紧急报警」，id 和内容对不上。

## 7. 前车扣住以后，后车全挤进区间

- 用户两张截图：
  - 099-2039 在陆家嘴下行扣车，094、028、113、012 四列车全部开进南京东路—陆家嘴的过江区间排队。G1405–G1501 一共 1624 m，挤了四列车。
  - 010-1335 在海天三路扣车（20:55–21:21），后面十来列车全部堆在川沙—凌空路一带。
- 现实 ATS 有「区间列车数限制」：下一个站间区间里已经有 N 列车时，后车在本站扣住不发车，这样乘客可以在站台下车，车也不会停在隧道里。仿真里没有这个功能（全仓搜不到）。
- 做法：
  - 每个站间区间的限车数写成数据，放在 `OPERATIONS` 里，默认 1 列。【假设】过江段同样是 1 列，有资料就按资料改。
  - 出站放行的判断只加在一处：发车条件里多一条「下一区间车数未满」。不要在别处另写一份扣车逻辑。
  - 扣在站台的车，状态栏和日志要写原因，例如「区间限车」。调度员手动放行时可以越过这个限制。
  - CM、RM 和救援车不受限车影响，只对 ATO 自动发车生效。
- 加测试：前车停在区间不动，后车停在上一站不发车；前车出清这个区间后，后车才发车。
- 加上以后，两种日型的计划不受影响（这是运行时的放行条件，不改运行图）。`trips`、`blocks` 哈希不变。

## 9. 加开被当天已有的库存不平衡挡住

- 用户截图（00:38）：加开一趟「川沙停车场出段 → 机场 → 回川沙」，00:54 发车，预览报「运行图不可行」：
  - 北翟路车辆段 夜间库存 38 列，次日早晨需 36 列；
  - 川沙停车场 夜间库存 30 列，次日早晨需 32 列。
  - 冲突时刻都是 01:23，也就是这趟加开回段的时间。
- 这趟加开从川沙出、回川沙，不改变任何一个车场的库存。这 ±2 是当天已经有的，很可能来自故障车退出服务或救援回了另一个车场。加开不该因为它被挡住。
- 根因有两处：
  - `planning.ts` 的加开预览只要有 error 就拒绝，没有跟改前的计划比。`standby.ts` 里已经有 `liveIssues` / `noWorse` 做这件事（`YARD_BALANCE` 计数不变就不算新问题）。
  - `noWorse` 自己也有漏洞：它按 `i.t >= sim.t` 过滤问题。`YARD_BALANCE` 的时刻取的是最后一次进出段，改前是 00:20 之类的早于现在的时刻，被过滤掉了；改后变成 01:23，又被算进来。结果同一个不平衡，改前看不见、改后算作新问题。
- 做法：
  - 把 `noWorse` 挪到两边都能用的地方，加开预览和备车接替都用它，不要再抄一份。
  - 比较前后问题时，`YARD_BALANCE` 这类全天汇总的问题不按时刻过滤，用 `code + 车场 + 计数` 比。只要加开没有让任何一个车场的差额变大，就放行。
  - 已有的不平衡在预览里作为提示列出来，不当成拒绝原因。
- 顺带查清楚：这一天的 ±2 是从哪里来的。用当天的事件，比如故障车退出服务、救援、手动加开，在探针里复现，看是哪一步把车送进了另一个车场，并确认这是现实中合理的处置。另外，运营日切换以后，次日的出段安排要按两个车场的实际库存来排（和第 3 条一起看）。
- 用户又试了一趟北翟路 01:54 出段 → 蟠祥路 → 回北翟路，被同一条拒掉，冲突时刻 02:32。这说明当天出现差额以后，任何加开都过不去。
- 同时发现：00:50–01:00 起有三段施工封锁（川沙—凌空路、张江高科—金科路、北新泾—威宁路），`planning.ts`、`timetable.ts` 都不知道有施工。加开的路径要是穿过已经封锁的区间，预览应该拒绝，并写明是哪一段施工；没穿过就放行。施工数据只从现有的封锁表里读，不要另建一份。
- 加测试：
  - 先人为造成北翟路 +1、川沙 −1 的不平衡，再加开一趟川沙出、回川沙的车：预览通过，并附带不平衡提示。
  - 加开一趟北翟路出、回川沙的车，使差额变大：预览拒绝。
