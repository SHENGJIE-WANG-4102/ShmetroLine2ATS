## 二、审计发现

### A1 worker 出异常时界面没有任何提示（高）

- 全 `src` 没有给仿真 worker 挂 `onerror`（`src/main.ts:38` 创建后无处理）。
- `src/sim/worker.ts` 的 tick 循环（`:394`）和 `stepOnce`（`:161`）没有 try/catch；仅有的两个 try 在预热缓存（`:93`、`:97`）。
- 跨日 `rollover()` 在 tick 里执行 `new Sim(config, old)`（`worker.ts:127`）。排图里有两处 throw：`timetable.ts:248`（缺过夜泊位）、`timetable.ts:1118`（无可用过夜出车任务）。
- 未核实：这两处 throw 是否在跨日重排的调用链上，没有追完。
- 后果：一旦抛出，画面定住，诊断包导不出来。对应 AGENTS.md「近期踩过的坑」第 4 条。

## 四、设计走向

### C1 等待关系做成一等数据

现在「近期踩过的坑」前三条（规则互相抵消、加规则补死锁、停车原因不说真话）是同一个结构问题：等待关系散落在 `ats.ts` 的大函数里，没有统一的表示。

方向：
- 每条等待规则返回结构化的原因：我是谁、在等谁（车 / 进路 / 设备 / 时刻）、哪条规则。
- 每个 tick 可以从这些原因建出等待图。图里出现环就是死锁，直接作为完整性检查的一项，报警里写出环上的每一条边。
- 规则只许改自己这列车的状态，这一点由类型约束（规则函数拿到的别的车是只读的）。
- `halt`、`arsWait` 的显示文本从同一份结构生成，不再手写。

效果：死锁从「压测跑出来再查」变成「出现的那一刻就报出是哪两条规则」。这也是拆 `ats.ts` 的自然切法：一条规则一个模块。

### C2 排图分阶段，每阶段有自己的校验

`layoutService` 505 行说明几个阶段混在一起。方向是拆成有明确输入输出的阶段：服务需求 → 时刻铺画 → 冲突平移 → 车底接续 → 出入段。每个阶段的产物可以单独落盘、单独对比，换数据后运行图变了能说清楚是哪一阶段变的。

### C3 线路能力模型

`LineData` 现在已有 `automation`、`signalling`、`dto`。继续往这个方向走，把每种运行模式定义成一项能力，公共代码只看能力：

- 每项能力有一条专用测试线（像 `testbranch` 那样），小到几站，先在测试线上把机制做对，再接真实线路；
- 真实线路 = 能力组合 + 数据。目标是没有新能力的直线线路只写数据，不动 `src/sim`；
- 加一个线路数据自检（启动时或脚本里）：泊位数与过夜规则对得上、每个交路端点有折返能力、能力声明与数据一致。这样 A1 里那类 throw 会在数据自检阶段报出来，而不是跨日时。

### C4 回放作为验收手段

诊断包回放已经有了。下一步把它用起来：
- 每次用户报的问题，诊断包进一个回归集（`tests/replays/`，注意不含不能公开的素材）；
- 大改动的验收是「回归集全部回放，逐项对比差异报告」，不看哈希。

### C5 界面测试

`src/ui` 42 个文件里只有 8 个测试文件引用它。界面的规矩是「同样输入同样输出」（坑 6），适合做纯函数快照：给定 snapshot，断言几何和文字，不需要开浏览器。

### 5.2 建议顺序

用户此前定的顺序是 14 → 11 → 1 → 3+4。下面在这个顺序上补了两处，理由写在每一步里。

1. **收尾 14号线，做完 11号线（Y 形）。** 前置：B4（方向判断清零）。完成标准：两条支线的交路在两种日型下排图 0 问题，汇合点的先后次序由数据定，两天随机压测 0 违例。
2. **10号线（建议插在这里）。** 它是 Y 形加 UTO，两项能力都已经有了。如果 C3 的目标成立，这条线应该几乎只写数据。它的价值是验证，做下来要动多少 `src/sim` 就是能力模型的成绩单。
3. **1号线（既有固定闭塞）。** 新能力：固定闭塞下的追踪和信号显示。先在测试线上做。注意资料表里 1号线的后备和降级模式是「未查到」，需要用户补现实情况。
4. **共线，然后环线，然后 3+4号线。** 这是全网最难的一组，拆三步：
   - 共线：两个线路组共用一段正线，涉及两张运行图在共线段的统一铺画、汇入次序、两线 ATS 的分工。先做两条 5 站测试线共用 2 站。
   - 环线：没有终点折返，车底连续运行，出入段在环上。方向辅助函数（硬规矩 7）是前提。
   - TACS：资料表里降级细则「未查到」，建议只做到「正常运行下的界面和授权显示」，不编降级行为。
5. **16号线（越行加编组 / 解编）。** 两项新能力，分开做：
   - 站内越行、快慢车时刻铺画。对排图阶段（C2）是最大的考验，所以放在 C2 做完之后。
   - 站台编组 / 解编运行（用户说明，2026-11-16）：车底在运营中合并和拆分，车底运用、泊位占用、站台对标、车次号都要跟着变。在哪些站、哪些时段编解组，需要用户给现实情况，不从资料推。先在测试线上做。
6. **其余直线线路（6、7、8、9、12、13、15、17、18）。** 到这一步应当是纯数据工作。每条线的瓶颈是数据：配线、首末班、间隔、场段。

**机场联络线（要做，用户决定，2026-11-16）**：它用 CTCS-2 加 ATO，列控和行车组织与地铁不是一套东西，需要新的信号能力，放在最后，按独立项目估。

**建议不做**：磁浮线、浦江线（胶轮 APM），理由同上，做了等于另写一个仿真。

### 5.3 每加一条线都要过的关

- 该线路数据自检通过（C3）；
- 两种日型排图 0 error，首末班对上官方；
- 两天带天气随机压测 0 违例；
- 测试线、2号线、14号线结果有变化的，写明变在哪、为什么；
- 改动公共代码的行数记下来。这是能力模型好不好用的直接度量，应该一条比一条少。

### 5.4 数据是真正的瓶颈

代码上每条直线线路的边际成本会越来越低，现实资料的成本不会。2号线的准确度来自用户的实地录音和 PIS 实拍，这一点别的线路没有。

建议把线路分两档，在界面上明示：
- **校准档**：有实地数据，区间时分、停站、运行等级有依据（现在只有 2号线）；
- **示意档**：只有官方首末班和间隔，区间时分按车辆性能和站间距推算，标【假设】。

这样可以先把全网铺开，不用等每条线都有实测。
